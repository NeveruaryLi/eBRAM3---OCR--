### 1.3 核心架构契约

#### 1.3.1 CaseHandler 契约

基类位于 `cases/base.py`，所有 Case Handler 必须继承并实现 4 个抽象方法：

| 方法 | 输入 | 输出 | 调用时机 |
|---|---|---|---|
| `analyze()` | session_id, session_store, session_results_store | `AsyncGenerator[SseEvent, None]` | `/pdf/session/analyze` 收到 POST |
| `generate_report()` | session_id, result_key, output_format, session_results_store | `(bytes, media_type, filename)` | `/pdf/session/download` 收到 POST |
| `followup_chat()` | session_id, text, conversation_id, session_results_store | `{"conversation_id": str, "reply": str}` | `/pdf/session/chat` 收到 POST |
| `get_downloadable_keys()` | session_id, session_results_store | `list[str]` | 路由层验证下载合法性时调用 |

**SseEvent 类型约定**（`cases/base.py:14`）：

```python
SseEvent(type="progress", data={"message": str, ...})      # 进度更新，流继续
SseEvent(type="result",   data={"result_key": str, ...})   # 一个结果完成，前端启用下载按钮
SseEvent(type="error",    data={"message": str, ...})      # 局部错误，流继续
# 致命错误 → raise 异常，路由层捕获后发 fatal_error 并关闭流
```

**注册新 Case**（`cases/__init__.py:20`）：

```python
REGISTRY: dict[str, type[CaseHandler]] = {
    "case1": Case1Handler,
    "case2": Case2MediatorBriefingHandler,
    "case5": Case5HkliiSearchHandler,
    "case4": Case4PdfTranslationHandler,  # ← Case 4 在此注册
}
```

#### 1.3.2 Session 数据流

三个全局 dict 定义于 `api/pdf_chat.py:70-77`：

| Store | 类型 | 存储内容 |
|---|---|---|
| `session_store` | `dict[str, list[DocResult]]` | Case 1/2：OCR + Agent A 原始结果；Case 5：`list[ScrapedResult]` |
| `session_metadata` | `dict[str, dict]` | `{"case_type": "case1"|"case2"|"case5", ...}` — 路由层 dispatch 依据 |
| `session_results_store` | `dict[str, Any]` | Handler 写入的最终分析结果（result_key → 文本） |

**Dispatch 逻辑**（`api/pdf_chat.py:466-480`）：

```python
def _get_handler(session_id):
    case_type = (
        session_metadata.get(session_id, {}).get("case_type")
        or session_results_store.get(session_id, {}).get("case_type", "case1")
    )
    return get_handler(case_type)
```

**写入时机**：
- Case 1/2：PDF 上传时通过 `/pdf/session/upload` 写入 `session_store`，同时写入 `session_metadata`
- Case 5：`/case5/scrape` 完成时写入 `session_store` 和 `session_metadata`（`case_type="case5"`）
- 所有 Case：`analyze()` 完成后 Handler 负责写入 `session_results_store`

**TTL 清理**（`api/pdf_chat.py:80-105`）：后台任务每 30 分钟清理 2 小时以上的 session，对没有 `created_at` 属性的对象（如 `ScrapedResult`）跳过 TTL 检查。

#### 1.3.3 SSE 事件系统

路由层统一序列化格式（`api/case5_routes.py:45-48`）：

```python
def _sse(event_type: str, data: dict) -> str:
    payload = json.dumps({"type": event_type, **data}, ensure_ascii=False)
    return f"data: {payload}\n\n"
```

**通用事件类型**：

| type | 发送方 | 说明 |
|---|---|---|
| `analysis_start` | 路由层 | analyze stream 开始前 |
| `analysis_complete` | 路由层 | generator 正常耗尽后 |
| `fatal_error` | 路由层 | 捕获到未处理异常 |
| `progress` | Handler | 进度提示 |
| `result` | Handler | 某 result_key 完成（附 `result_key` 字段） |
| `error` | Handler | 局部错误 |

**Case 5 特有事件**：`scrape_complete` / `no_results` / `search_timeout`

**前端解析**：`static/common.js` 的 `parseSSE()` 统一解析，各 Case 的 `.js` 文件 switch 分发不同 type。

## 章节 3：开发经验与陷阱

### 3.1 调试/排查最佳实践

**用 `headless=False` 观察 DOM 时序**：Playwright 在 headless 模式下某些元素会比 non-headless 提前出现（Vuetify 骨架屏），排查「无结果 selector」时必须用 `headless=False` + DevTools 手动观察，不能依赖快照截图。

**等待多个互斥 selector 替代单一超时**：Case 5 最初用 `wait_for_selector("tr.resultrow", timeout=120_000)`，导致无结果时傻等 2 分钟。正确做法：`wait_for_selector("tr.resultrow, tr.v-data-table__empty-wrapper", timeout=30_000)`，然后 `query_selector` 判断哪个先出现。

**静态代码分析 > 盲跑日志**：诊断「开始生成摘要走错 Agent」bug 时，用 `Grep` 扫描 `static/*.js` 中反斜杠路径比对日志高效得多。如果某个端点没有访问日志，先确认 URL 构造是否正确，再看日志。

**确认诊断再执行，不盲猜**：发现疑似 bug 后，先 grep 全量确认影响范围，再动代码。Case 5 诊断过程中曾误判 fetch URL 有反斜杠，后来用 Python `repr()` 确认文件内容才发现是 Grep context 行的显示问题，实际 URL 正确。

### 3.2 前端开发陷阱

**JS 模板字符串中反斜杠会被吃掉**：`` `\pdf\session\analyze` `` 在 JS 中实际是 `pdfsessionanalyze`，因为 `\p`、`\s`、`\a` 不是合法转义序列，反斜杠被 ECMAScript 规范静默丢弃。URL 路径**始终用正斜杠**。

**复制已有 case.js 改造时必须全量审查**：端点 URL、DOM 元素 ID、状态变量名（`scrapedResults` vs `fileQueue`）都需要对应修改，漏改会导致功能串台（如追问请求路由到错误的 Agent）。

**`scrapeSessionId` 决定追问路由**：Case 5 中 `shouldUseAnalysisChat()` 返回 `!!scrapeSessionId`；`resetCurrentView()` 会把 `scrapeSessionId` 清空，之后追问会走 Agent B 而非 Case5Handler。这是「先追问后摘要」UX 问题的根本原因。

**折叠面板状态要在 `resetCurrentView()` 同步重置**：`isSearchCollapsed`、toggle 按钮显隐、`compactKeyword` 的 hidden 属性需要在「新对话」按钮点击时统一复位，漏掉任一项会导致界面残留。

### 3.3 后端开发陷阱

**Playwright sync API 不能在 asyncio event loop 中直接调用**：必须通过 `loop.run_in_executor(executor, sync_func, *args)` 桥接。executor 建议全局单例（`_EXECUTOR = ThreadPoolExecutor(max_workers=6)`），避免每次请求创建线程池。

**Session TTL 清理要用 `hasattr` 检查**：Case 1/2 的 `DocResult` 有 `created_at`，Case 5 的 `ScrapedResult` 没有。清理函数对 `docs[0]` 判断前加 `hasattr(docs[0], "created_at")` 防止 `AttributeError`（`api/pdf_chat.py:93`）。

**超时阈值要留余量**：HKLII 国际访问有时延迟高，等待结果元素建议 25-30s（测试中 15s 太短会误触发 SearchTimeout），页面加载 GOTO 设 60s。

**GPTBots payload 中 document 是列表不是对象**：`"document": [doc_item]` 而非 `"document": doc_item`，格式不对 Agent 会静默忽略附件，仅回复文字。这是 D1 决策的核心要点，任何新 Case 都要严格遵守。

**Agent J 调用在 `analyze()` 中全链路是 async + httpx**：不要误用 requests（同步），Case 5 的 `_ask_agent_j()` 用 `httpx.AsyncClient`，timeout 设 300s（Agent J 分析 10 条案例需要较长时间）。

### 3.4 与产品对齐的协作模式

**重要决策必须 D 编号固化**：每个不显而易见的技术选择（payload 格式、存储位置、超时阈值）都要编 D-Case5-N 格式，写入上下文文档，避免跨 session 反复讨论。

**DOM 探索/数据探索类任务必须先停下报告**：Case 5 开发中「无结果 selector 是什么」这类问题必须先用 `headless=False` 实际观察，报告给用户确认后再实现，不能盲猜（HKLII 用 Vuetify 数据表，selector 与标准 HTML 表不同）。

**Plan 模式处理多文件改动**：凡是一次性改 4 个以上文件的功能（如 v0.2 三项优化），先出完整 Plan 文档，用户审核后统一实施，避免中间状态 commit。

**批次实施 + 一次性 commit**：多项优化合并为一次 commit，Git 历史保持线性可读。

**预期流程**：

```
用户上传 PDF + 选翻译方向（中→英 / 英→中）
    ↓
PyMuPDF 逐页转 PNG（model/pdf_processor.py 已有 PyMuPDF 基础）
    ↓
逐页 PNG → Agent I（GPTBots blocking 模式，图片 base64 + 翻译方向文字）
    ↓ SSE progress 每处理一页推一次
按页码顺序收集翻译后图片（bytes）
    ↓
合并为译文 PDF
    ↓
写入 session_results_store，yield SseEvent(type="result", ...)
前端启用下载按钮
```
